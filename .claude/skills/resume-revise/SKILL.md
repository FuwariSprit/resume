# レジュメ修正

`/resume-review` の結果を踏まえ、**採否をユーザーに確認したうえで**新しいバージョンを作ります。

## 手順

### 1. レビュー結果を読む

引数 `$1` にバージョン番号があればそれを、なければ `drafts/reviews/` の最新のものを対象にします。
`vN-antipattern.md` / `vN-quality.md` / `vN-vision.md` / `vN-fidelity.md` を全部読みます。

対応するレビュー結果がない場合は、先に `/resume-review` を実行するよう案内して終了します。

### 2. 全指摘を一覧表示する

観点ごとに、指摘IDと一行見出しと深刻度を一覧にします。
ユーザーが判断できる程度の情報量にとどめ、レビューファイル全文の再掲はしません。

```text
## アンチパターン (AP)
- AP-1 [high] 「全3名」だけで案件の中身が書かれていない（プロジェクトサマリパターン）
- AP-2 [medium] ...

## 企業側評価軸 (QA)
- QA-1 [high] ...
```

指摘の詳細（なぜ問題か・修正案）を見たいと言われたら、その時に該当箇所を見せてください。

### 3. 採否を確認する

**AskUserQuestion で、観点ごとに採用する指摘を選んでもらいます**（`multiSelect: true`）。

一括で反映しないでください。レビュアーの指摘がすべて正しいとは限らず、
本人にしか判断できない事情（意図的にそう書いている、資料側が間違っている、
今は書けない事情がある）があります。判断はユーザーのものです。

進め方:

- 観点ごとに1問ずつ聞く（4問）。1問に全観点を混ぜると選択肢が多くなりすぎます
- 指摘が多い観点は、深刻度 high から順に確認し、必要なら複数回に分けます
- 選択肢のラベルは指摘ID＋一行見出し、説明に「なぜ問題か」の要約を入れます
- 「一部だけ採用したい」「修正案とは違う形で直したい」という要望が出たら、
  選択肢に頼らず対話で確認してください

事実の追加が必要な指摘（fidelity の欠落指摘や、`<!-- 要確認 -->` の解消）は、
この場では反映できません。採用されても「要ヒアリング」として保留し、手順6で案内します。

### 4. 新しいバージョンを作る

採用された指摘だけを反映し、`drafts/resume-v(N+1).md` に**新規ファイルとして**書き出します。

**`drafts/resume-vN.md` は上書きしません。** 何をどう変えたかを後から差分で追えるようにするためです。

反映するときの原則:

- 採用されなかった指摘に関係する箇所は**触らない**。
  ついでの改善は、ユーザーが承認していない変更なので入れないでください
- 一次情報源（`docs/` 配下）にない事実を、修正のついでに補わない。
  修正案に「本人への確認が必要」とある内容は、勝手に埋めずに保留する
- 修正案をそのまま貼るのではなく、前後の文脈に合う文章に整える
- 文章スタイルは `.claude/skills/resume-build/references/writing-style.md` に従う。
  修正で文章を書き足すときも、文体・改行・字数上限・リストの使い方・造語の避け方は同じ規約です。
  書き足しで開発単位が長くなったときは、同ファイルのコマンドで字数を数え直してください

### 5. 採否の記録を残す

`drafts/reviews/vN-decisions.md` に、全指摘の採否を記録します。

```markdown
# 採否記録: v1 → v2

日付: YYYY-MM-DD

| ID | 深刻度 | 見出し | 採否 | 備考 |
| --- | --- | --- | --- | --- |
| AP-1 | high | ... | 採用 | v2 の職務経歴に反映 |
| QA-3 | medium | ... | 見送り | <ユーザーの判断理由。聞けていれば書く> |
| FD-12 | high | ... | 保留 | 追加ヒアリングが必要 |
```

見送りの理由は、聞けた範囲で書いてください。
次のバージョンで同じ指摘が再び出たときに、判断済みかどうかがわかります。

### 6. 次の一手を案内する

- 保留（要ヒアリング）がある場合: `/resume-interview <対象>` で不足分を埋めてから
  `/resume-build` に戻ることを提案する
- 修正が入った場合: `/resume-review v(N+1)` で再レビューできることを案内する
- 内容が固まった場合: `resume.md` へ反映し、`pnpm lint` を通す流れを案内する
  （`drafts/` は lint 対象外なので、反映時に初めて文章チェックがかかります）
