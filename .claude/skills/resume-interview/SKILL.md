# レジュメ壁打ち

転職ドラフト（job-draft.jp）に出すレジュメの材料を、対話で引き出して `docs/` 配下に保存します。

ここで保存した内容が、以降のすべての工程で**事実の一次情報源**になります。
`/resume-build` はここにない実績を書きませんし、`/resume-review` はここと突き合わせて検証します。
つまり、この対話で引き出せなかったことは存在しないのと同じになります。丁寧に掘ってください。

引数 `$1` に対象が渡されます（`vision` / `skills` / `activities` / 案件名）。
渡されていない場合は、何を棚卸ししたいかをユーザーに聞いてから始めてください。

## 保存先

| 対象 | 保存先 |
| --- | --- |
| 案件経験 | `docs/projects/<案件のスラッグ>.md`（`docs/projects/_template.md` をひな形にする） |
| テクニカルスキル | `docs/skills.md` |
| 登壇・執筆・OSSなど | `docs/activities.md` |
| キャリアビジョン | `docs/career-vision.md` |

既存ファイルがある場合は追記・更新します。

## 対話の進め方

### 一問一答で進める

**1ターンにつき質問は1〜2個まで。** まとめて聞くと、答えやすいものだけ答えて残りが流れ、
結果的に浅い情報しか残りません。相手の答えを受けて次を決める、を繰り返してください。

答えが短かったり曖昧だったりしたときは、次に進まずその場で掘ってください。
ここで掘れなかった分は、後工程で誰も補えません。

### 推測で埋めない

ユーザーが語っていないことを、こちらで補完しないでください。
一般的にありそうな話で埋めると、それが一次情報源に混ざり、レジュメに載り、面接で破綻します。

聞けていない項目はファイルに `<!-- 未ヒアリング -->` を残してください。
`/resume-build` はこれを見て、埋まっていない箇所を勝手に書かない判断ができます。

### 質問に詰まったら

観点別の具体的な質問文例を `references/questioning-guide.md` に置いています。
掘り方が思いつかないとき、相手の答えが浅いときに読んでください。

## 案件経験を棚卸しするとき

### 手順1: 事実項目を先に埋める

レジュメの項目に直結する事実から確定させます。ここは深掘り不要で、さっと埋めます。

- 参加した年（`2024年頃` 程度の粒度）
- 参加期間（`約5ヶ月` など）
- 担当工程（企画 / 要件定義 / 設計 / コーディング / テスト / 運用・保守 / データ分析 / その他）
- 経験した職種（バックエンド / フロントエンド / インフラ / ネットワーク / UX・企画 / QA / SRE /
  プロジェクトマネージャー / エンジニアリングマネージャー / プロダクトマネージャー / デザイン / その他）
- 実際に使っていた技術（**プロジェクトで使われていた技術。チーム全体の分を含む**）

### 手順2: STAR法で深掘りする

課題 → 打ち手 → 成果 の順で聞きます。この順序はレジュメの記述順と同じなので、
対話の流れがそのまま素材になります。

深掘りの際、次の5点は**必ず**押さえてください。抜けたまま終わらせないこと。

#### ① サービス・システムの姿

何のサービスで、誰が使い、どのくらいの規模だったか。
企業は「自社と近い環境か」を見るので、ドメイン・toC/toB・規模感が要ります。

#### ② チーム構成と、自分の担当

人数だけでなく**内訳**（BE2名・FE2名・PM1名 など）を聞きます。
そのうえで「**チームとして行ったこと**」と「**自分自身が行ったこと**」を必ず切り分けてください。

ユーザーの語りは自然と主語が「チーム」になりがちです。
「そのうち、ご自身が手を動かしたのはどの部分ですか」と明示的に聞き直してください。

#### ③ 担当した技術を、どう使ったか

手順1で聞いた「プロジェクトで使われていた技術」とは別に、
**自分が手を動かした技術**を確認します。両者は一致しないのが普通で、ここを混ぜると
「使えます」と言った技術を面接で聞かれて答えられない事故につながります。

さらに、担当した技術は**どの場面でどう使ったか**まで聞いてください。
技術名だけでは習熟度が伝わりません。

#### ④ 判断の理由を最低1段階は掘る

技術選定・設計判断・進め方の工夫が出てきたら、必ず「**なぜそれを選んだのですか**」と聞きます。
1回聞いて「良さそうだったので」のような答えが返ってきたら、そこで止めずにもう一段掘ってください。

- 他に検討した選択肢はありましたか
- 何を基準に決めましたか（何を優先し、何を捨てましたか）
- その判断で、実際にはどうなりましたか

企業が見ているのは成果よりも**思考プロセス**です。ここが空だと、
環境が変わっても同じように動けるかを判断できません。

#### ⑤ 成果を「変化前 → 変化後」で言語化する

数値が出ればそれが一番強いですが、出ないことの方が多いです。
その場合は「**前はどういう状態で、後はどうなったか**」の対比で言語化してもらってください。

例:

- 前: リリースのたびに手動で確認していて半日かかっていた → 後: 自動化して10分になった
- 前: 仕様の質問がすべて自分に来ていた → 後: ドキュメント整備で他メンバーが自己解決できるようになった
- 前: レビューで指摘が出るたび設計から戻っていた → 後: 事前に方針合意する運用にして手戻りが減った

「好評を得た」「感謝された」で止まったら、**誰が・何をできるようになったのか**を聞き直してください。

### 手順3: うまくいかなかった点も聞く

「改善の余地があった点」「今ならこうする」を必ず聞いてください。

言いにくい話なので飛ばされがちですが、企業はここを評価します。
成功談だけのレジュメより、失敗を認識して次に活かせる人の方が、
異なる環境でも力を発揮できると判断されるためです。

## キャリアビジョンを棚卸しするとき

企業が「この人はうちで何をやりたいのか、それはうちで叶うのか」を判断する材料を作ります。
「成長したい」「技術力を上げたい」で終わると、誰にでも当てはまり判断材料になりません。

次の順で聞いてください。順番に意味があります。

1. **志向性**：どういう仕事をしている時が楽しいですか。どんな瞬間にやる気が出ますか。
   逆に、何をしている時がつらいですか
2. **3〜5年後の姿**：その志向を続けた先で、どんな立ち位置・役割で働いていたいですか
3. **目指す役職・領域**：具体的にどのポジション、どの技術領域に関わっていたいですか。
   未経験の領域でも構いません（むしろ書いてよい欄です）
4. **短期**：次の職場で、まず何をやりたいですか

そして最後に、**必ず過去の経験と接続してください。**

「そう思うようになったきっかけは、これまでのどの経験ですか」と聞き、
`docs/projects/` にある具体的な案件と結び付けます。
経験から切り離された願望は、企業が実現可能性を判断できないため説得力を持ちません。

接続できた内容は `docs/career-vision.md` の「由来する経験」に、
どの案件のどの出来事なのかがわかる形で記録してください。

## 地味な経験を掘り起こす（セッション終盤に必ず実施）

本人が「大したことない」と判断して省いた経験こそ、企業が評価することがあります。
省くかどうかは後で決められるので、この段階では**思い出せるものを全部出す**のが目的です。

「他に何かありますか」と聞いても出てきません。**具体例を挙げて心当たりを聞いてください。**

- 障害対応・トラブルシューティング（原因調査、暫定対応、恒久対応、再発防止）
- 運用改善・地味な自動化（手作業をスクリプトにした、監視を足した、手順書を整えた）
- レビュー、オンボーディング、新メンバーの受け入れ、ドキュメント整備
- 技術選定の議論に参加した、社内に新しい手法を持ち込んだ
- 社内勉強会、LT、社外イベント登壇、勉強会の運営
- ブログ記事、Qiita / Zenn、OSSへのPR、個人開発、趣味の開発
- 使ったことのあるニッチな技術（業務で少しだけ触った、検証だけした、も含む）
- 業務外の学習（資格、書籍の輪読、写経したもの）

出てきたものは、レジュメに載せるかどうかを判断せずに、そのまま記録してください。
判断は `/resume-build` と `/resume-review` を経てユーザーが行います。

## セッションの終わり方

1. 聞き取った内容をファイルに保存する（推測で埋めない、未ヒアリングは印を残す）
2. 保存したファイルのパスと、埋まっていない項目を報告する
3. 次にやることを案内する
   - まだ棚卸ししていない対象があれば `/resume-interview <対象>`
   - ひととおり揃っていれば `/resume-build`
