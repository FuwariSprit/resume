# レジュメ作成

`docs/` 配下の一次情報源から、転職ドラフト（job-draft.jp）用のレジュメドラフトを組み立てます。

骨格と ①〜⑦ の対応の正本は `assets/resume-template.md`、
構造の規約と文体・字数の正本は `references/writing-style.md`、
キャリアビジョン欄の構成の正本は `references/career-vision-structure.md` です。
このファイルは**手順と、作成時の判断の原則**だけを持ちます。

## 手順

### 1. 一次情報源を読む

`docs/` 配下をすべて読みます（`docs/projects/*.md` の `_template.md` と `README.md` は除く、
`docs/skills.md`、`docs/activities.md`、`docs/career-vision.md`）。

`<!-- 未ヒアリング -->` が残っている項目を数えてください。
主要な項目（案件の①〜⑦、キャリアビジョン）に多く残っている場合は、
先に `/resume-interview` に戻ることを提案し、それでも続けるかユーザーに確認してから進みます。

**リポジトリ直下の `resume.md` は一次情報源ではありません。** 過去に書かれた古い版なので、
内容の根拠には使わないでください。

### 2. 出力先を決める

`drafts/` の既存ファイルを確認し、次の番号を決めます。初回は `drafts/resume-v1.md`。
既存のバージョンは**絶対に上書きしません**（差分を後から追えるようにするため）。

### 3. テンプレートに沿って書く

`assets/resume-template.md` を読み、その構成で書き出します。
①〜⑦をどのセクションに配分するかは、同ファイル冒頭のコメントにある対応表が正です。

あわせて **`references/writing-style.md` を必ず読み、その規約に従って書いてください**。
文体・改行・字数上限・リストの使い方・造語の避け方・固有名詞の表記が定めてあります。

キャリアビジョン欄は、内容要件（下記「キャリアビジョンに書くこと」）を満たしたうえで、
`references/career-vision-structure.md` の6ブロックの順序に沿って構成します。

### 4. 提示する

提示するドラフトは、次を満たしている必要があります。

- 一次情報源に根拠がない記述が混ざっていない（特に数値と、役割・担当範囲の表現）
- `#### 概要 / チームおよび担当 / 開発・実装 / 振り返り` の4セクションと、
  `■` → `【課題】【打ち手・取り組み】【成果】` の3階層になっている
- 「実際に使っていた技術」（チーム全体の環境）と、本文に織り込んだ「自分が使った技術」が
  混同されていない
- `references/writing-style.md` の規約を満たしている。とくに次の3点
  - 1開発単位あたり800字前後（同ファイルのコマンドで数える）
  - リストが短い並列項目の列挙にとどまり、課題→打ち手のような文脈が散文で書けている
  - 自分が作った複合語・言い回しが混ざっていない（例: 「〜障害」「〜化」）

そのうえで、生成したパスと、`<!-- 要確認 -->` を付けた箇所を報告し、
`/resume-review` に進むよう案内します。

## 書くときの原則

### 一次情報源にない実績を創作しない

これが最も重要です。理由は `docs/README.md` にあるとおりで、
レジュメに書いたことは面接で必ず確認されるため、一次情報源が事実の上限になります。

自然に思える補完も禁物です。「Laravelを使ったならEloquentも使っただろう」のような推測、
「3名チームなら当然レビューもしただろう」のような常識的な補完は、
どちらも本人が語っていない以上、創作です。

判断に迷う箇所は、盛らずに `<!-- 要確認 -->` を付けて残してください。
`/resume-review` の fidelity レビュアーがこの印を拾い、ユーザーが確認できます。

### 表現は強めてよいが、事実は動かさない

一次情報源のメモは口語で断片的なので、そのまま貼らずに整った文章に書き直します。
謙遜した表現（「〜しただけです」「小規模ですが」）は、企業に貢献が伝わらなくなるため、
事実を変えない範囲で自信のある表現に直して構いません。

ただし次は事実の改変にあたるので、してはいけません。

- 資料にない数値を出す
- 「担当した」を「主導した」「リードした」に格上げする
- チームがやったことを、自分がやったこととして書く
- 資料の「たぶん」「〜だと思う」を断定に変える

### 情報を絞りすぎない

企業はニッチな経験や地味な運用改善、社外活動も評価します。
「これは大したことないから省こう」という判断は、あなたがするものではありません。
一次情報源にあるものは基本的に載せ、載せる/載せないの判断はユーザーに委ねてください。

分量が多くなること自体は問題ありません。読みにくくならないよう構成で整理してください。

### 複数企業が読む前提で書く

特定1社のJDに最適化しません。社内用語や、その会社の組織構造を知らないと読めない記述は、
一般的な言葉に置き換えるか、短い補足を添えてください。

### キャリアビジョンに書くこと

`docs/career-vision.md` を元に、次が読み取れる文章にします。

- 志向性（何にやる気が出るか、根底にある価値観）
- 3〜5年後にどういう立ち位置でいたいか、目指す役割・領域
- **それが過去のどの経験に由来するか**（職務経歴に書いた案件と結び付ける）
- 次の職場で短期的にやりたいこと

経験と接続していない願望は、企業が実現可能性を判断できないため説得力を持ちません。
`docs/career-vision.md` に由来する経験が記録されているなら、必ず反映してください。
