# レジュメ作成

`docs/` 配下の一次情報源から、転職ドラフト（job-draft.jp）用のレジュメドラフトを組み立てます。

## 手順

### 1. 一次情報源を読む

`docs/` 配下をすべて読みます。

- `docs/projects/*.md`（`_template.md` と `README.md` は除く）
- `docs/skills.md`
- `docs/activities.md`
- `docs/career-vision.md`

`<!-- 未ヒアリング -->` が残っている項目を数えてください。
主要な項目（プロジェクト詳細の①〜⑦、キャリアビジョン）に多く残っている場合は、
先に `/resume-interview` に戻ることを提案し、それでも続けるかユーザーに確認してから進みます。

**リポジトリ直下の `resume.md` は一次情報源ではありません。** 過去に書かれた古いドラフトなので、
内容の根拠には使わないでください（Markdownの体裁を参考にする程度にとどめます）。

### 2. 出力先を決める

`drafts/` の既存ファイルを確認し、次の番号を決めます。初回は `drafts/resume-v1.md`。
既存のバージョンは**絶対に上書きしません**（差分を後から追えるようにするため）。

### 3. テンプレートに沿って書く

`assets/resume-template.md` を読み、その構成で書き出します。

### 4. 自己チェックしてから提示する

書き終えたら、生成物を読み返して次を確認してください。

- 一次情報源に根拠がない記述が混ざっていないか（特に数値と、役割・担当範囲の表現）
- 各案件のプロジェクト詳細が①〜⑦の順になっているか
- 「実際に使っていた技術」と、③で書いた「自分が使った技術」が混同されていないか

そのうえで、生成したパスと、`<!-- 要確認 -->` を付けた箇所を報告し、
`/resume-review` に進むよう案内します。

## 書くときの原則

### 一次情報源にない実績を創作しない

これが最も重要です。レジュメに書いたことは面接で必ず確認されるため、
本人が語っていない話が載っていると、その場で説明できず信頼を失います。
一次情報源が事実の上限だと考えてください。

自然に思える補完も禁物です。「Laravelを使ったならEloquentも使っただろう」のような推測、
「3名チームなら当然レビューもしただろう」のような常識的な補完は、
どちらも本人が語っていない以上、創作です。

判断に迷う箇所は、盛らずに `<!-- 要確認 -->` を付けて残してください。
`/resume-review` の fidelity レビュアーがこの印を拾い、ユーザーが確認できます。

### 表現は強めてよいが、事実は動かさない

一次情報源のメモは口語で断片的なので、そのまま貼らずに整った文章に書き直します。
謙遜した表現（「〜しただけです」「小規模ですが」）は、企業に貢献が伝わらなくなるため、
事実を変えない範囲で自信のある表現に直して構いません。

ただし次は事実の改変にあたるので、してはいけません。

- 資料にない数値を出す
- 「担当した」を「主導した」「リードした」に格上げする
- チームがやったことを、自分がやったこととして書く
- 資料の「たぶん」「〜だと思う」を断定に変える

### 情報を絞りすぎない

企業はニッチな経験や地味な運用改善、社外活動も評価します。
「これは大したことないから省こう」という判断は、あなたがするものではありません。
一次情報源にあるものは基本的に載せ、載せる/載せないの判断はユーザーに委ねてください。

分量が多くなること自体は問題ありません。読みにくくならないよう構成で整理してください。

### 複数企業が読む前提で書く

特定1社のJDに最適化しません。社内用語や、その会社の組織構造を知らないと読めない記述は、
一般的な言葉に置き換えるか、短い補足を添えてください。

## 出力の構成

`assets/resume-template.md` が正です。骨格だけ再掲します。

```text
# 職務経歴書
## 個人情報
## キャリアビジョン
## テクニカルスキル
## 職務経歴
### <期間> <案件名>（<会社名>）
#### 参加した年
#### 参加期間
#### 担当工程
#### 経験した職種
#### 実際に使っていた技術
#### プロジェクト詳細
## その他の活動
## 趣味
```

### 「プロジェクト詳細」の書き方

①〜⑦の順に、見出しを立てずに散文で書きます。
⑤⑥⑦の並びが「課題 → 打ち手 → 成果」にあたり、この順序が読み手の理解を助けます。

| # | 書くこと | 押さえる点 |
| --- | --- | --- |
| ① | どんなサービス・システムか | 規模・ドメイン・toC/toB。企業が経験の背景を想像できるようにする |
| ② | あなたは何を担当したか | チーム構成の内訳を書き、**チームとして行ったこと / 自分が行ったこと**を区別する |
| ③ | どんな技術を用いたか | 列挙で終えず「**どの場面でどう使ったか**」まで書く。習熟度はここで伝わる |
| ④ | どんな機能を開発したか | 開発した機能を具体的に挙げる |
| ⑤ | どんな課題に取り組んだか | 課題の背景と「**なぜその行動をとったのか**」を書く |
| ⑥ | どんな工夫をしたか | 「**なぜその技術・アプローチを選んだか**」の判断理由まで書く |
| ⑦ | どんな成果を出したか | 数値で示す。数値がなければ**変化前→変化後**の対比で書く |

一次情報源に「改善の余地があった点」が記録されている場合は、⑦のあとに続けて書いてください。
うまくいかなかった点と、そこから何を得たかは、
企業が「異なる環境でも力を発揮できるか」を判断する材料として評価されます。

### 各項目の粒度

- **参加した年**: `2024年頃` のように年単位
- **参加期間**: `約5ヶ月` のように期間の長さ
- **担当工程**: 企画 / 要件定義 / 設計 / コーディング / テスト / 運用・保守 / データ分析 / その他
  から該当するものを列挙
- **経験した職種**: バックエンド / フロントエンド / インフラ / ネットワーク / UX・企画 / QA / SRE /
  プロジェクトマネージャー / エンジニアリングマネージャー / プロダクトマネージャー / デザイン / その他
  から該当するものを列挙
- **実際に使っていた技術**: プロジェクトで使われていた技術の一覧（**チーム全体の分を含む**）。
  自分が手を動かした技術は③で「どう使ったか」とセットで書くので、ここでは区別しない

「実際に使っていた技術」と③を混同しないでください。前者はプロジェクトの環境、後者は本人のスキルです。
混ぜると、触っていない技術を「できる」と主張したことになります。

### キャリアビジョン

`docs/career-vision.md` を元に、次が読み取れる文章にします。

- 志向性（何にやる気が出るか、根底にある価値観）
- 3〜5年後にどういう立ち位置でいたいか、目指す役割・領域
- **それが過去のどの経験に由来するか**（職務経歴に書いた案件と結び付ける）
- 次の職場で短期的にやりたいこと

経験と接続していない願望は、企業が実現可能性を判断できないため説得力を持ちません。
`docs/career-vision.md` に由来する経験が記録されているなら、必ず反映してください。
