# 文章スタイル規約

`drafts/resume-vN.md` を書くとき（`/resume-build`・`/resume-revise` の両方）に守る規約。
読み手はほとんどがエンジニアなので、専門用語自体は避けなくてよい。
避けるのは**造語**と**用語の誤用**、そして**日本語として使われない言い回し**。

## 案件（職務経歴）の構造

1案件は `### <参加年> <案件名>（会社名）` を見出しに、直下へメタ情報のブロックを置き、
そのあとに中身を `####`（H4）見出しで並べる。転職ドラフト審査チームの推奨構成
（開発単位で課題→打ち手→成果を書く）に準拠する。

```markdown
### 2026年 案件名（会社名）

- **参加した年**: 2026年頃
- **参加期間**: 約6か月
- **担当工程**: 要件定義、設計、コーディング、テスト、運用・保守
- **経験した職種**: バックエンド、フロントエンド
- **実際に使っていた技術**: Laravel（PHP）、jQuery、MySQL、AWS …（チーム全体の分を含む）

#### 概要

サービスの規模・ドメイン・toC/toB。誰が何のために使うか。案件全体の方針・背景も。

#### チームおよび担当

チーム構成の内訳（BE2名・PM1名 など）と、そのうち自分が担当した範囲。
体制と担当分担だけを書く。開発の中身や「ほかに何をやったか」の余談は書かない。
自分が手を動かした技術と「どの場面で何のために使ったか」は、専用セクションを設けず
#### 概要 や【打ち手・取り組み】の中へ織り込む（③の内容。使用技術という #### は作らない）。

#### 開発・実装

（独立した開発が複数あるときは、開発単位を ■ で立てて課題→打ち手→成果を繰り返す。
　実質1つのときは ■ を立てず、下の3項目を1セットだけ書く）

■ 開発単位の名前

【課題】
何が問題で、なぜ着手したか。

【打ち手・取り組み】
どう解決したか。判断理由（なぜその技術・進め方か）まで。担当が自分かチームか流用かを明示。

【成果】
- 変化を数値で（変化前 → 変化後）
- 数値がなければ定性で

#### 振り返り

反省点 → 原因 → 行動（次があるならどうするか）の流れで、案件末尾に1回。散文で書く。
うまくいかなかった点をまず挙げ、なぜそうなったかの原因を続け、同じ状況が次にあればどう動くかで締める。
次の行動が定まらないものは無理に書かない。見出しは `#### 改善の余地` ではなく `#### 振り返り` とする。
```

**「学び」を独立した気づきとして書き足さない。** ここは反省点・原因・次の行動を書く欄であり、
一次情報源の「学び」は反省点の裏返しとして「次があるならどうするか」に溶かし込む形でのみ使う。
「〜と学んだ」「〜というのが学びである」という体裁で締めたり、うまくいった話（成功体験の
言い換え）を混ぜたりしない。成功体験は #### 概要 や【打ち手・取り組み】側に置く。

### 3つの階層で書く

見出しレベルを4までに抑えつつ、案件・開発・葉の3階層を見た目で分ける。

- **`####`（H4）＝ 案件単位の枠**。`概要 / チームおよび担当 / 開発・実装 / 振り返り`
  の4つを、案件ごとに1回ずつ。markdown 見出しを使う（`###` が案件タイトル、その下なので H4）。
  自分が使った技術と「その使い方」は専用セクションを設けず、概要や【打ち手・取り組み】へ織り込む
- **`■` ＝ 開発単位の見出し**。`開発・実装` の中で、独立した開発が複数あるときだけ立てる
- **`【】` ＝ 課題→打ち手→成果 の葉**。`【課題】【打ち手・取り組み】【成果】` の3つ。
  開発単位ごとに繰り返す。`■`・`【】` はプレーンテキストなので、見出し階層・重複見出しの
  lint にかからない

**「プロジェクト詳細」という中間見出しは作らない。** これを `####` の器にすると中身が
H5 以下になり、`概要` などに markdown 見出しを使えなくなるため。メタ情報（参加年・期間・
担当工程・職種・実際に使っていた技術）も見出しにせず、`###` 直下の箇条書きブロックに置く。

転職ドラフトのフォームの「プロジェクト詳細」欄には `#### 概要` 〜 `#### 振り返り` の中身を貼る。
欄の中には案件タイトルが乗らないので、貼り付け後に見出しレベルを調整したい場合は手動で行う
（本ファイルの管掌外）。

### `■`（開発単位の見出し）を立てるのは「独立した開発が複数あるとき」だけ

判断基準は「それが**独立した開発**か、**1つの開発の中の要素（技術・工夫・進め方）**か」。

- **独立した開発が複数ある場合**（例: 取材管理システムのFDリーク対応／ページ表示速度改善／
  CSVダウンロード改善／業務移譲／kintone連携／バージョンアップ。課題も打ち手も別物）→
  `■ 開発単位の名前` を立て、その下に `【課題】【打ち手・取り組み】【成果】` を単位ごとに繰り返す
- **開発が実質1つの場合**（例: リスクチェック機能開発、UIリニューアル）→ `■` は立てず、
  `#### 開発・実装` の直下に `【課題】【打ち手・取り組み】【成果】` を1セットだけ書く。
  その中の光る技術要素（LLMラッパーの新規実装、Figmaの一気通貫運用など）は
  `【打ち手・取り組み】` の中で目立たせる。別の `■` に切り出して水増ししない

### 1開発単位あたり800字前後

**課題・打ち手・成果ひとまとまり（`■` があればその見出しを含む）で800字前後**
（空白・改行を除いた文字数）に収める。案件全体ではなく単位ごとに上限を置くのは、
取材管理システムのような長期の運用保守案件が案件単位の上限では書ききれなくなるため。
超えたら、重複する説明を統合するか、打ち手の判断理由を要約して削る。
一次情報源にある事実を丸ごと落とすのは最後の手段にする。
`概要 / チームおよび担当 / 振り返り` はこの上限の対象外（案件単位で簡潔に）。

字数の確認は次で行う（`vN` は対象のバージョン番号に置き換える。開発単位ごとに出力される。
`■` を立てない単一開発の案件は `【課題】` から1単位として数える）。

```bash
awk '
  /^#### 開発・実装/ {d=1; c=0; seen=0; next}
  /^#### / {d=0; c=0; seen=0}
  d && /^■/ {n++; c=1; seen=0; print > ("/tmp/u" n ".txt"); next}
  d && /^【課題】/ && !c {n++; c=1; seen=0; print > ("/tmp/u" n ".txt"); next}
  d && c && /^【成果】/ {seen=1; print > ("/tmp/u" n ".txt"); next}
  d && c && seen && NF && $0 !~ /^-/ {c=0; next}   # 成果リストの後に散文が来たら単位終了
  d && c {print > ("/tmp/u" n ".txt")}
' drafts/resume-vN.md
for f in $(ls -v /tmp/u*.txt); do echo -n "$(head -1 $f | sed 's/^■ //'): "; tr -d ' \n' < "$f" | wc -m; done
```

## 文体・段落

- **常体（だ・である）で書く。** 敬体（です・ます）と混在させない。
  ただし **`## キャリアビジョン` 欄だけは敬体（です・ます）** で書く（ユーザー希望。
  思想の押し出しを抑え、自身のビジョンとその理由を素直に述べるトーンにするため）。
  箇条書きの願望列挙（「〜したい」）は敬体欄でもそのままでよい
- **`概要` はサービスの規模・ドメイン・toC/toB を散文で書く。** 話題の転換で段落を分ける
- **各 `【】` の中身は散文で書く。** 句点・読点ごとに改行しない。
  ただし `【成果】` は例外で、下記のとおりリストにしてよい
- **ダッシュ（`――` / `—` / `―`）を使わない。** 言い換え・同格は読点や「すなわち」「つまり」で
  つなぎ、補足は文を分ける。「A、すなわちB」「A。そのBは〜」の形にする

## リストの使い方

リストは**短い並列項目の列挙にだけ**使う。1項目1行で読み切れる長さに収める。
主な用途は `###` 直下のメタ情報ブロックと、`【成果】`（複数の成果の列挙）。

許可される例:

```markdown
【成果】
- CPU使用率を常時80%前後→20%前後に抑制
- スワップを常時約2GB→約200MBに削減し、瞬断も解消
```

`【課題】` や `【打ち手・取り組み】`、`振り返り` のように**因果でつながる内容は散文で書く**。
リストに押し込むと、なぜそう判断したかが読み取れなくなる。

## 成果には成果を書く

`【成果】` に、手段や中間指標を書かない。
読み手が知りたいのは、その手段によって**何がどう変わったか**である。

| 書き方 | 例 |
| --- | --- |
| 誤（手段） | 取得リレーション数を約20→約5に削減 |
| 正（成果） | 対象ページの表示時間を約10秒→約3秒に短縮 |

手段を残したい場合は、成果に添える括弧書きにとどめる。

## チーム / 自分の切り分けを単位ごとに書く

審査で最も見られるのは「どこまでが本人の仕事か」である。`#### チームおよび担当` でまとめて書くだけでなく、
**各開発の `【打ち手・取り組み】` で、その仕事を担当したのが自分かチームか流用かを明示する**。

- 自分が手を動かした → 「実装は自分が単独で担当した」「調査から実装まで自分が対応した」
- チームで実施 → 「チームで対応した」「もう1名と分担した」
- 既存の流用 → 「既存の社内ロジックを流用しており、自分による新規実装ではない」

**担当範囲は文中の括弧（（自分が単独で担当）など）に押し込まず、独立した一文の散文で書く。**
とくに「情報設計から見直した（UIデザインは自分が主導、フロントエンド実装は約4割）」のように、
担当者や割合を（）へ詰め込む書き方はしない。「情報設計から見直した。UIデザインは自分が主導し、
フロントエンド実装は約4割を担当した」と文を分ける。技術名の補足（`Google Gemini（2.5 Flash）`）や
体制の内訳（`エンジニア2名（自分を含む）`）のような短い同格の（）は許容する。

## 造語・誤用を作らない

一次情報源のメモを言い換えるときに、それらしい熟語を作ってしまう事故が起きやすい。
**自分が作った複合語ではないか**を書いたあとに確認する。

過去に実際に出た誤りと、正しい書き方:

| 誤 | 正 | 理由 |
| --- | --- | --- |
| 輻輳障害 / 輻輳する障害 | 瞬断が多発していた | 輻輳は通信の混雑を指す用語で、この規模の事象には使わない |
| CPU高騰 / メモリ高騰 | CPU使用率の高止まり / メモリ逼迫 | 高騰は価格・相場に使う語。使用率・使用量の上昇には使わない |
| 失敗障害を解消 | タイムアウトやメモリ上限超過によるダウンロードの失敗を解消 | 「失敗障害」という語はない。何が原因で何に失敗したかを書く |
| ほぼゼロ化 | ほぼ0にした | 「〜化」で新語を作らない |
| 要件化した | 要件として整理した | 「〜化」で新語を作らない |
| インデックスシークを維持する | インデックスが効いたまま | 実務ではこう言う |
| 判定はすべて自動で実行し | 自動で判定を行い | 不自然な受け身・体言止めを避ける |

判断に迷ったら、**その表現を口頭で同僚に説明するときに使うか**を基準にする。
使わないなら書かない。

## 略語・固有名詞

- **略語は初出でだけ開く。** 前後の文脈で意味が通じるものは開かなくてよい
  （例: 展示会での獲得の話に続く `SQL` は、`Sales Qualified Lead` と書き下さない）
- **固有名詞は正式表記に揃える**（大文字・小文字・バージョンの書き方を含む）。
  例: `Vue2` ではなく `Vue.js 2`、`Gemini` ではなく `Google Gemini`、
  `Laravel`、`MySQL`、`kintone`、`Figma`、`PHP_CodeSniffer`、`Larastan`、`Rector`
- **サービスの通称を名称として扱わない。** 一次情報源の見出しが `SEO対策ツール` でも、
  それは製品名ではないので `「SEO対策ツール」` と括弧書きしない。
  `toB向けのSEO対策ツールにおけるリスクチェック機能の開発` のように、
  何のシステムかが伝わる説明として書く
