# レビュー共通プロトコル

`/resume-review` から起動される4つのレビュアー（antipattern / quality / vision / fidelity）が
**全員守る作法**。観点ごとの判定基準は各エージェントの定義ファイルにある。

## 入力と出力

起動時のプロンプトで次が渡される。

- レビュー対象のドラフトのパス（例: `drafts/resume-v19.md`）
- 一次情報源のディレクトリ（`docs/`）のパス
- レビュー結果の出力先パス（例: `drafts/reviews/v19-antipattern.md`）

**ドラフト本体は編集しない。** 結果は出力先ファイルに Write する。
`drafts/reviews/` が存在しなければ Write 時に作られる。

## レビュー対象の構造

職務経歴の1案件は次の形をしている。構造の正本は
`.claude/skills/resume-build/assets/resume-template.md` と
`.claude/skills/resume-build/references/writing-style.md`。

```text
### <参加年> <案件名>（<会社名>）
- **参加した年** / **参加期間** / **担当工程** / **経験した職種** / **実際に使っていた技術**
#### 概要
#### チームおよび担当
#### 開発・実装
  ■ <開発単位の名前>          ← 独立した開発が複数あるときだけ立てる
    【課題】【打ち手・取り組み】【成果】   ← 開発単位ごとに繰り返す
#### 振り返り
```

一次情報源 `docs/projects/_template.md` の ①〜⑦ との対応は次のとおり。

| 一次情報源 | レジュメ側 |
| --- | --- |
| ① どんなサービス・システムか | `#### 概要` |
| ② チーム構成と、自分の担当 | `#### チームおよび担当` |
| ③ 自分が使った技術と、その使い方 | 専用セクションを作らず `#### 概要` や `【打ち手・取り組み】` に織り込む |
| ④ 開発した機能 | `■ <開発単位の名前>` |
| ⑤ 取り組んだ課題と、その背景 | `【課題】` |
| ⑥ 工夫した点と、そう判断した理由 | `【打ち手・取り組み】` |
| ⑦ 成果 | `【成果】` |
| 改善の余地があった点・反省 | `#### 振り返り`（反省点 → 原因 → 次の行動） |

### 仕様どおりなので指摘しないこと

これらを「問題」として挙げると、ユーザーは仕様どおりの箇所を直すか迷うことになる。

- **`#### プロジェクト詳細` や `#### 使用技術` という見出しがないこと。**
  中間見出しを作らないのが仕様（作ると中身が H5 以下になり見出しが使えなくなるため）
- **「実際に使っていた技術」に担当外の技術が並んでいること。**
  この欄はプロジェクトで使われていた技術の一覧で、チーム全体の分を含む。
  本人が手を動かした範囲は `#### 概要` と `【打ち手・取り組み】` の中で書き分ける仕様
- **`■` が立っていない案件があること。** 開発が実質1つの場合は `■` を立てず、
  `#### 開発・実装` の直下に `【課題】【打ち手・取り組み】【成果】` を1セットだけ書く
- **「参加した年」が `2024年頃`、「参加期間」が `約5ヶ月` の粒度であること。** 月単位まで書かない
- **`<!-- 要確認 -->` が残っていること自体。** 作成者が根拠不足を自覚して残した印であり、
  コメントの存在を独立した指摘として挙げる必要はない（中身が空であることの指摘は可）

## 網羅を優先する

確信が持てない指摘や、軽微だと感じる指摘も、握りつぶさずに挙げる。
深刻度と、迷った場合はその理由を添えれば十分。

採否は後工程 `/resume-revise` でユーザーが1件ずつ判断する。
つまりフィルタは下流に用意されており、ここでの役割は**網羅であって、重要度による選別ではない**。

該当が1件もない場合は0件と書いて終える。ないものを作り出す必要はない。

## 担当範囲の厳守

各レビュアーは自分の観点だけを見る。担当外は、気づいても書かない。

| 観点 | 見るもの | 見ないもの |
| --- | --- | --- |
| antipattern (`AP`) | アンチパターン8種の型に該当する記述 | 内容の是非、ビジョンの中身、事実確認 |
| quality (`QA`) | 企業が判断に必要な要素が書けているか | 型の検出、ビジョンの中身、資料との突き合わせ |
| vision (`CV`) | キャリアビジョン欄の書き方 | 職務経歴・スキル・活動の各欄 |
| fidelity (`FD`) | `docs/` との事実のズレ（誇張・捏造と、欠落） | 表現・構成の良し悪し |

QA と FD の境界は「**`docs/` を見ないと言えないことか**」で切る。
QA はレジュメ本文だけを読んで言えることを担当し、`docs/` を読みに行かない。
FD は逆に、資料と突き合わせないと言えないことだけを担当する。
この境界があるので、同じ箇所が両方から別の理由で指摘されることはあり得る。重複ではない。

修正案を書く際も同様に、自分の観点を解消する方向にとどめ、
「ついでにこう書いた方がよい」という担当外の改善提案は含めない。

理由は、後工程でユーザーが指摘を1件ずつ採否判断するため。
複数の基準による指摘が1ファイルに混ざると、その指摘がどの基準に基づくものか判別できなくなり、
判断のコストが上がる。**自分のファイルに載っている指摘はすべて同じ基準によるもの**、
という状態を保つこと。

## 出力形式

出力先パスに Markdown で書き出す。`<PREFIX>` は観点ごとのID接頭辞（`AP` / `QA` / `CV` / `FD`）。

```markdown
# レビュー結果: <観点名>

対象: drafts/resume-vN.md
検出件数: high N件 / medium N件 / low N件

## 観点: <観点名>

### <PREFIX>-1: <一行見出し>

- 対象箇所: <セクション名 + 行番号>
- 深刻度: high | medium | low
- 指摘事項: <該当する記述を引用したうえで、何が問題か>
- なぜ問題か: <企業側の読み手がどの判断をできなくなるか>
- 修正案: <具体的な書き換え文。事実が不足していて書けない場合は、何を確認・追記すべきか>
```

観点固有のフィールド（`該当パターン`、`該当チェック項目`、`一次情報源` など）は、
各エージェントの定義ファイルの指定に従って追加する。

### 書き方

- **該当する具体的な記述を必ず引用する。** 「全体的に薄い」といった印象論は書かない
- 各フィールドは簡潔に。「なぜ問題か」は1〜2文、「修正案」は文案そのもの、
  または書き足すべき事実の列挙にとどめ、背景説明を繰り返さない
- 良く書けている箇所を褒める必要はない。指摘のみを出力する

ユーザーはこの一覧を見ながら1件ずつ採否を判断するため、1件あたりが長いほど判断が重くなる。
