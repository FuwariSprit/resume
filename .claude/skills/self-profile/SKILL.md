# セルフプロフィールの聞き取り

転職サービスのプロフィール欄に入力する次の3項目を、対話で引き出して1ファイルにまとめます。

| 項目 | 入力欄に表示される質問文 |
| --- | --- |
| 今後身につけたい技術 | エンジニアとして今後身につけたいと思っている技術を教えてください |
| パフォーマンスを出せる環境 | あなたが一番パフォーマンスを発揮できるのはどんな環境ですか？ |
| 他人から評価されるポイント | エンジニアとしてのあなたの強みや、他人から評価されているポイントは何ですか？ |

**書き出す文章は、この質問文への回答として成立している必要があります。**
項目名だけを見て書くと、聞かれていることからずれます。

出力先は `profile/self-profile.md`（1ファイル・上書き更新）。
入力欄にそのままコピペできる状態で書き出します。

引数 `$1` に対象が渡されます（`tech` / `environment` / `strengths`）。
渡されていない場合は3項目すべてを順に扱ってください。

## このスキルの位置づけ

`/resume-interview` → `/resume-build` → `/resume-review` → `/resume-revise` の
レジュメ作成フローとは**独立した単発のスキル**です。次の点が異なります。

- **ドラフトのバージョンを採番しない。** レビューと改訂のループがないため、`profile/self-profile.md` を上書き更新します
- **レビュー用Subagentの対象外。** `.claude/agents/` の4つは起動しません
- **`docs/` の内容が上限にならない。** 「`docs/` にない実績は書かない」は職務経歴のルールです。
  この3項目は職務経歴ではないので、`docs/` に記録がなくても対話で聞いて書けます

## 先に読むもの

対話を始める前に、材料がすでにあるか確認してください。同じ話を聞き直すと相手の負担になります。

| ファイル | 何の材料になるか |
| --- | --- |
| `docs/skills.md` | 「今後身につけたい技術」の起点。**今できること**との差分が、身につけたい技術になる |
| `docs/career-vision.md` | 「パフォーマンスを出せる環境」の材料。環境への言及がすでにあることが多い |
| `docs/projects/` | 「他人から評価されるポイント」の裏づけになる案件 |

読んだうえで、**すでに書いてあることは「こう書いてありますが、今もそうですか」と確認する形にし、
ゼロから聞き直さないでください。**

なお `docs/skills.md` が空の場合、「今できること」が確定していないため
「今後身につけたい技術」を差分として書けません。その場合は先に
`/resume-interview skills` を案内してください。それでも進めたい場合は、
対話の中で現状のスキルレベルを都度確認しながら進めます。

## 対話の進め方

### 一問一答で進める

**1ターンにつき質問は1〜2個まで。** まとめて聞くと答えやすいものだけ答えて残りが流れます。

### 推測で埋めない

ユーザーが語っていないことを補完しないでください。

特に「他人から評価されるポイント」のうち**他者評価の部分は事実の主張**であり、面接で
「それは誰に言われたんですか」と必ず確認されます。
こちらが「こう言われたのでは」と補完したものが提出されると、その場で破綻します。
強みの主張（本人の自己申告）と、他者から言われた事実は、対話の中でも切り分けてください。

聞けていない項目は `<!-- 未ヒアリング -->` を残してください。

## 1. 今後身につけたい技術

> エンジニアとして今後身につけたいと思っている技術を教えてください

技術名の羅列にしないことが目的です。「Goを学びたい」だけでは誰にでも書けます。

次の3点がセットで揃うまで掘ってください。

1. **現状どこまで触ったか**（未経験 / 素振りだけ / 業務で少し / 業務で常用）
2. **なぜ必要だと感じたか**
3. **すでに着手していることがあるか**（個人検証、書籍、勉強会など）

### 掘り方

「何を学びたいですか」から入ると、流行っている技術名が並びます。
**実体験の欠落から入ってください。**

- 直近の業務で「これができれば違ったのに」と思った場面はありますか
- 今の環境では経験できないとわかっている領域は何ですか
- 個人開発や検証で触ってみて、もっと深くやりたいと思ったものはありますか

「なぜ学びたいのですか」に対して「流行っているので」「よく聞くので」で止まったら、
そこで止めずにもう一段掘ります。**その技術を身につけた自分が、何をできるようになるのか**まで
言語化してもらってください。

### 注意

業務外での検証（触ってみたが導入には至らなかったもの）は、**弱い実績ではなく強い材料**です。
「導入しなかったので大したことない」と本人が省こうとしたら、拾い上げてください。
学びたい理由に実際の検証が伴っていることは、意欲の裏づけになります。

## 2. パフォーマンスを出せる環境

> あなたが一番パフォーマンスを発揮できるのはどんな環境ですか？

願望ではなく**過去の実績から**組み立てる欄です。
「風通しのいい環境で働きたい」は誰にでも当てはまり、判断材料になりません。

### 掘り方

- これまでで一番仕事が進んだ・力が出たと感じた時期はいつですか。**その時、何がそろっていましたか**
- 逆に、力が出せなかった時期はありますか。**何が足りませんでしたか**
- 任され方（裁量の範囲、意思決定の距離、レビューの厚さ、チーム規模、相談できる専門職の有無）は
  どうなっていると力が出ますか

具体的な状況が出てきたら、そこから条件を抽象化します。
「あの案件では事業責任者と直接話せた」→「意思決定者との距離が近い環境」のように、
**事実 → 条件**の順で言語化してください。逆順（条件を先に挙げて事実を後付け）にすると、
それらしいだけの文章になります。

### 注意

不満の裏返しをそのまま書かないでください。
「開発投資が少ない環境は嫌だ」は、読み手には現職への不満として届きます。
**「〜がないと困る」で出てきた答えは、必ず「〜があると力が出る」の形に反転させてから記録します。**

## 3. 他人から評価されるポイント

> エンジニアとしてのあなたの強みや、他人から評価されているポイントは何ですか？

質問文のとおり、この欄は**強み（自己申告）と他者評価の2階建て**です。
どちらか片方だけでは弱くなります。

- **強みだけ**（自己申告のみ）→ 根拠がなく、読み手が真に受けられない
- **他者評価だけ**（言われたことの列挙）→ 本人が何を武器にしているのかが見えない

**強みを主張として立て、それが他者からも見えていることを裏づけとして添える**形にします。

### 掘り方

まず**エンジニアとしての強みを挙げてもらいます**（技術領域、設計、進め方、越境の仕方など）。
そのうえで、挙がった強みそれぞれに**他者から見えている証拠**を紐づけてください。

証拠として使えるものは、次まで確認します。

- **誰が**（上長 / 同僚 / 他部署 / クライアント / コミュニティの参加者）
- **いつ・どういう文脈で**（人事評価、1on1、レビュー、障害対応中、イベント後 など）
- **具体的に何と言われたか**、または**どういう事象があったか**
- 紐づく案件があれば、`docs/projects/` のどれか

裏づけが出てこない強みは、削らずに残して構いません
（強みの主張自体は本人が語ってよい範囲です）。ただし
**言われてもいない評価を、こちらが証拠として作り出さないでください。**
裏づけのない項目には `<!-- 裏づけ未確認 -->` を残します。

### 証拠が出てこないときの聞き方

「褒められたことはありますか」と聞いても出てきません。**具体例で心当たりを聞いてください。**

- 人事評価や1on1で、繰り返し言われることは何ですか
- チームの中で「これはあなたに聞こう」と相談が来るテーマは何ですか
- レビューを頼まれるのは、どういう種類のコードや資料ですか
- 新しいメンバーが入ったとき、何を教える役割になりますか
- 社外（勉強会、コミュニティ、クライアント）で反応があったことは何ですか

**「よく相談されること」は特に有効です。** 本人が無自覚な強みが出やすく、
かつ他者評価としての裏づけが最初から付いています。

### 注意

言われた言葉が抽象的な場合（「丁寧だよね」「頼りになる」など）、
**その人が何を見てそう言ったのか**を聞いてください。
評価の言葉だけを並べても、読み手は再現性を判断できません。

## 出力

`profile/self-profile.md` に、次の構成で書き出します。

```markdown
# セルフプロフィール

<!-- 転職サービスのプロフィール欄に貼る用。/self-profile で更新する -->

## 今後身につけたい技術

## パフォーマンスを出せる環境

## 他人から評価されるポイント
```

### 書き方

- 文体・表記のルールは `.claude/skills/resume-build/references/writing-style.md` に従います
  （常体、造語を作らない、略語・固有名詞の表記）
- 各欄はそのままコピペする前提なので、**入力欄に貼って成立する文章**にします。
  このファイル内でしか意味が通らない参照（「上記のとおり」など）は書かない
- 聞き取れた事実の範囲を超えて、文章を盛らないこと

## セッションの終わり方

1. `profile/self-profile.md` を保存する
2. 保存したパスと、埋まっていない項目を報告する
3. **職務経歴の材料になる事実が出てきていたら、`docs/` への追記を提案する**

3が重要です。この対話では、職務経歴側の裏づけになる事実がしばしば出てきます。
たとえば「他人から評価されるポイント」で出た上長からの具体的な評価は、
案件の成果の裏づけになります。該当する `docs/projects/<案件>.md` や `docs/skills.md` への
追記を提案してください（ユーザーが承諾したら追記する。勝手に書かない）。
