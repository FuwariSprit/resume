## 志向性

<!--

根底にある欲求は「自分の思想・ブランドを多くの人に知ってもらいたい」「成果物に自分の思想を強く反映したい」というもの。
人生で成し遂げたいことを聞かれたら、なるべく自分を知っている人を増やしたい、それも名前や顔だけでなく考え方・思想の方向性を把握した人を増やしたい、と考えている。

その欲求は特に「視覚的に見えるもの」に対して強く出る（認知特性として、視覚的に見えるものの方が認知しやすい傾向があると自己分析している）。
たとえば「このサービスのバックエンドを担当した」「認証システムを担当した」「決済システムを担当した」よりも、「この画面・このサービスの体験を考えた」と言える方がテンションが上がる。
そのため、UI/UXデザイン、グラフィックデザイン、イベント企画、アプリケーション設計など「思想が色濃く出る」領域に強く惹かれる。

人が便利になるものを作ることはもちろん大前提として大事だが、それ以上に重視したいのは「自分がいいと思ったから作った」という、自分の意思決定を起点にできること。

趣味で運営しているTRPG・アナログゲームのコミュニティ運営が、この思想の具体例になっている。
「TRPGプレイヤーは議論が好きで、開発と同じように議論をぶつけ合って高め合ってほしい」という考えから、開発コミュニティのLT文化をTRPGコミュニティに持ち込んでLTイベントを開催したり、コンベンションを開いたりしている。
イベントの企画・方針・テーマや、それを視覚的に表現するポスター・バナーのデザインなど「思想が色濃く出る部分」は必ず自分の手で行い、逆に運営（実行）の部分は人に任せる、という役割分担をしている。

苦手・つらいと感じるのはプロジェクト管理。個人開発やコミュニティ運営（自分事化しやすいもの）ではリスクを深く考えた上で対策を打ちアクションに起こせているが、業務で自分の思想にうまく紐付けられないテーマだと思考が途中で止まってしまい、リスクが見えていてもその危険度に気付けず後回しにしてしまうことがある。

また、人にタスクを振る・人を頼ることも苦手（現在は振り返って改善中）。自分の思想を成果物に強く反映したいという欲求が邪魔をして、任せた部分にも結局自分で手を動かしてしまい、任せた相手と自分の両方に無駄な稼働がかかってしまった経験がある。

### 「一言で言うなら」についての示唆（レジュメ用の材料）

ドラフト（`drafts/resume-v8.md`）の「キャリアビジョンを一言で言うなら」は
「自分がいいと思った体験を、UXの検討からデザイン、実装、効果検証まで自分の手で通し切り、
それを多くの人が使うプロダクトで実現できる人材になりたい」となっているが、
本人はニュアンスが違うと感じている（反映先は `/resume-build` 側の判断に委ねるが、材料として残す）。

- 「自分の手でやり切る」という**手段レベルの話ではない**。もっと抽象度の高い、
  「自分の思想・ブランドを多くの人に知らしめたい」という欲求が核にある
- ここでの「ブランド」とは、他者から見て「この人はきっとこう考えるだろう」
  「この人のデザインはきっとこんな感じだろう」と伝わる状態を指す。特定のプロダクトの成果よりも、
  自分という個人に紐づく思想の伝わり方を重視している
- 対象は体験・UIに限らない。グラフィックデザインなども含め、
  「これは自分が作ったものだ」と他者から紐づけられる状態が理想
- 思想を広めるだけでなく、それを**「ちゃんと使ってもらえるもの」にしてビジネスとして稼ぐ**ところまでが目標。
  この構造は本ドキュメント末尾「参考にしている人・キャリア」で触れているcatnose氏への憧れと同じ
- 根底には「死ぬまでに自分の思想・ブランドを知っている人をなるべく増やしたい」という、
  人生単位の欲求がある

## AI時代における体験・UIの重要性についての考え

<!-- なぜ今、体験・UI領域に張るのか。AI時代の必然性として本人が言語化した選択理由。 -->

本人は、AI時代にUI/UX・体験の重要性はむしろ上がると考えている。論拠は次のとおり。

- ビジネスロジックの重要性は下がっていく。AIで再現しやすいため
- 一方でビジネスデータの重要性は上がる。AIでは簡単に再現できないため
- そしてもう一つ重要なのが「そのプロダクトが愛されるかどうか」。見た目がきれい・良さそうなUIは
  AIでどんどん作れるようになるが、真に手触りが良く、愛したくなるプロダクトは、
  手法としてAIを使っても簡単には作れないと考えている
- プロダクトのインターフェースを通したユーザーとのコミュニケーション、そこで醸成される信頼・愛着は、
  AIを使っても容易には作れない。だからこそ、より体験を重視していく必要があると考えている

「愛されるプロダクト」を分けるものについては、次のように言語化している。

- 大前提はユーザーファースト（ユーザーの課題を解決し、手触りが良いこと）。
  ただし、それだけなら他のプロダクトでも代替できる
- その上で、**作り手の考え・美学・思想がユーザーに見える／感じ取れること**が必要。
  「このプロダクトはこういう考えだから好きだ」とユーザーが感じ取れる部分があるかどうか
- 強い思想・美学に感銘を受けたり共感したりすることでファンが生まれる。
  それがあるかどうかが「愛される」の分かれ目だと考えている

この考えは、本人の核である「自分がいいと思った思想を成果物へ色濃く反映したい」という志向と地続きである。
作り手の思想を反映することこそが、AI時代に簡単には真似されない「愛されるプロダクト」を生む、
という位置づけになっている。

## 3〜5年後にどうありたいか

<!-- どういう立ち位置・役割で働いていたいか。できるだけ具体的に -->

まだ軸を定めきれていない部分だと本人が認識している。現時点で言語化できているのは以下。

やりたいこととして明確なのは、UXを考えるところから効果検証までを一通りやり切れる人材になること。具体的には次の流れ。

1. UXを考える
2. ユーザーインタビューなどさまざまな手段で情報収集し、自分の考えが妥当であることを確認する
3. 提案する
4. デザインを行う
5. 実装する（現時点ではバックエンドの方が圧倒的に得意）
6. リリースする
7. 効果検証を行う

一方で、ずっとプレイヤーでいたいわけではない。理由は収入の伸びしろで、現職を含め、マネジメント方面（組織マネジメント／エンジニアリングマネジメントなど）の方が役職手当などで収入が伸びる傾向にあると認識しているため、収入を伸ばすには何らかの役職に就く必要があるのではないかと考えている。

### PdMは「違う」と感じている理由

一時期「自分はPdMをやりたいのだ」と思い込んでいた時期があったが、業務内容を知って違うと感じた。理由は3つ。

- PdMはプロダクト全体を見る役割だが、自分が思想を強く反映したいのは「目に見える部分」に限定される
- 数値をゴリゴリ理詰めで積み上げて意思決定していくやり方は、やりたいことでもないし得意でもないと感じている。
  自分の思想・考えを強く反映しようとすると数値では説明のつかない部分が多く残るうえ、視覚・ビジュアル・体験で訴えかけるものは定量評価しづらく、そこに強い苦手意識がある
- PdMはプロジェクト管理能力を持った先にある役職だと捉えているが、プロジェクト管理は業務での成功例がほとんどない。
  不得意を伸ばすより得意を伸ばした方がよいと考えている

### 「PM力がないとPdMになれない」という思い込みの経緯（深掘り）

この思い込みのきっかけは、以前PdMをやりたいと上長に相談した際、
「プロジェクトマネジメントが安定してできていないとPdMにはなれない」と言われたこと。
当時は違和感がありつつも、実際に自分は推進力・先回り力・リスクマネジメントが不足していると自覚があり、
「PdMに限らずどんな仕事でも必要な力が自分には足りていないのだから、PdMは無理だろう」と納得してしまっていた。

その後、この思い込み自体を本人は次のように捉え直している。

- 自分は新しい挑戦が億劫になると理由を作って避けてしまう傾向がある（回避傾向の自覚）。
  「PM力が足りないからPdMもできない」は、この回避傾向による言い訳だった可能性があると振り返っている
- 現職でできなかったのは、現職の人員規模・体制（人が少なく担当範囲が広すぎた）による面もあり、
  環境が変われば同じ結論にはならないかもしれないと考えている

### PMとPdMの違いの再定義

深掘りの結果、本人は両者の違いを次のように言語化した。

- **PM**：プロジェクトを納期通りに着地させるためであれば、なんだってやる役割
- **PdM**：プロダクトを成功・成長させるためであれば、なんだってやる役割

この再定義によって「PM力の延長線上にPdMがある」という以前の認識は本人の中で崩れている。
一方で、この再定義は新たな不安も生んでいる。「プロダクトの成功のためになんだってやる」という定義の中には、
本人が苦手・苦痛と感じる「開発と関係のない調整業務」が含まれる可能性が高く、
その調整業務ばかりになることへの恐れがある。SEO対策ツールのUIリニューアルで経験した
「デザイン課題発見→提案→検証→調整→実装→リリース」の流れの中でも、調整業務自体は好きではなく、
辛さを伴うものだったと振り返っている。

そのため、現時点の結論としては「PdMという肩書き・役職そのものを目指すか」は保留しつつ、
「体験・UIの意思決定権を持ちながら、調整業務の比率が一定以下に抑えられる立場」を志向する、という方向に傾いている。

### UIデザイナーとも違う

「昔からUIデザイナーになりたいわけではない」「UIデザイナーを名乗りたいわけではない」とも述べている。

### 現時点で近いと感じている方向（対話で絞り込んだもの）

以下が感覚に近いと本人が選択した。肩書き（PdM／デザインエンジニア等）自体にはこだわりがなく、
「やりたいことができるか」を軸に考えている。

- **プロダクトの体験領域のリード**：プロダクト全体ではなく「体験・UI」の意思決定権を持つリード。
  数値責任はPdMに預け、体験の良し悪しの最終判断を自分が持つ立ち位置
- **体験設計を意思決定する立場**：「バックエンドを理解したフロントエンド」として、
  UX設計〜実装まで越境しつつ、最終的には体験設計そのものを意思決定できる立場

なお、以前「デザインエンジニアの旗振り役（職能を組織に定義・浸透させる立場）」という表現を記録していたが、
これは聞き手（Claude）側からの提案であり、本人自身の言葉ではなかったことが今回の深掘りで判明したため削除した。
「組織に職能を浸透させる」という部分は本人にとってしっくりこない一方、
「体験設計を意思決定する立場」の部分は本人の感覚と一致している。

「調整業務中心のリード」になることへの不安は本人も自覚しており、得意ではなく成功体験も少ない領域だと認識している。
ただし「ずっとプレイヤーでいることにも限界がある」とも感じており、
苦手を理由に避け続けるのではなく、成長の余地がある領域として向き合いたいという意向を持っている。

人のマネジメントについては「やりたいわけではないが、収入・裁量を得る手段として必要なら引き受ける」というスタンス。

### 段階的なキャリアパス（現時点のイメージ）

次の4段階で進むイメージを持っている。ただし各段階の期間感は明確ではなく、
「③体験設計を任せられる立場」に3年後までに到達したい、という目安のみ言語化できている状態。

1. バックエンドの強みを活かしつつ、フロントエンド比重を上げた立ち位置で入社する
   （これまでの業務ではバックエンド比重が高く、フロントエンドの経験を意図的に増やしたい段階）
2. その中でUI/UXの意思決定ラインに関与していく
3. 体験設計そのものを任せられる立場になる（3年後の目安）
4. 体験設計を意思決定する立場（リード）に進む

段階的キャリアパスの実現性についてのフィードバック（転職先選びの段階で「UI/UX意思決定に関与できるポジションか」を
明確な条件にしないと3年では届かない可能性がある、という指摘）については、本人は次のように受け止めている。

- 条件には含めたいが、「フロントエンドエンジニアとして入る」線も消したくない
  （UI/UX意思決定への関与とフロントエンドからの入社は、必ずしも二者択一ではないという認識）
- 「UI/UX意思決定への関与」と「給与・待遇」が完全にトレードオフになる場面が来た場合は、**給与・待遇を優先する**
- 転職ドラフトを利用しているため、見極めの順序としては
  「自分のキャリアビジョンに魅力を感じた企業からオファーが来る」→「その中から給与・待遇も含めて選ぶ」という流れを想定している。
  そのため、レジュメのキャリアビジョン欄自体を、体験・UI領域の意思決定や成長環境を提供できる企業に
  「この人が欲しい」と思わせられる内容に仕上げる必要があると認識している

## 次の職場で短期的にやりたいこと

<!-- 入社してすぐ、まず何をやりたいか。逆に、もうやりたくないこと -->

### やりたいこと

SEO記事作成画面のUIリニューアルやSEOリスクチェック機能で経験した、次の一連の流れをより高い精度でやり切れるようにしたい。

1. デザイン課題を発見する
2. 課題に対して提案を行う
3. ユーザーインタビューなどを通して検証する
4. ステークホルダーと調整する
5. 実装する
6. リリースする

### やりたくないこと・避けたいこと

- 開発投資が少なくなり、悪い意味で「安定した」プロダクトには入りたくない。
  運用保守や小さなリファクタリングを続けるだけで、積極投資や攻めたことができない環境はなるべく避けたい

### 環境として求めるもの

前提として、本人は「大きなサービス・大きな組織で働くとどうなるのかは、正直わからない部分が多い。
それも含めて、素直な興味として一度体験してみたい」と述べている。
そのうえで、現時点で言語化できている理由は以下。

- **より大きなサービス規模**：現職で担当してきたプロダクトはアクティブユーザーが3桁を超えることがなかった。
  UI/UXデザインでは、少数のクライアントに強くフォーカスして機能を作ることが多く、
  逆に社会的な少数派を考慮せずに作ることも多かった。アクセシビリティへの準拠は現職で一度も議題に上がったことがない。
  「多数にとって使いやすいUI・UXとは何か」を考える経験を積みたい
- **規模を前提にした設計経験**：ユーザー規模を想定したパフォーマンス設計の経験がない。
  たとえば前段にCDNやキャッシュ層を置き、どの程度キャッシュヒットさせる必要があるかを設計するような、
  利用者が多いからこそ必要になる技術の導入経験がない
- **より大きな組織規模**：現職はエンジニアが10人未満で、各事業部も人が少ない。
  デザイナーは現在もおらず、デザインを相談できる相手がいない。QAがいる環境も経験したことがない。
  専門職・プロフェッショナルが多い場に身を置いて自分のスキルを伸ばしたい。
  また、人が多いからこそ起きる新技術の取り入れや議論に参加したい
- **組織として技術・体験に投資できる環境**：現職は開発に割ける予算が少なく、
  R&D・新技術の検証・基盤技術の検証・より良いCI/CDの検証を組織として行える環境ではなかった。
  実質的に個人の持ち出し（「個人としてやってみたので使ってみましょう」）に委ねられていた。
  これは技術に限らずデザイン・UXも同じで、規模と体力があるからこそ、
  機能だけでなく体験の部分にも投資できると考えている

優先順位として、上位2つは「規模を前提にした設計経験」と「組織として技術・体験に投資できる環境」。

### 大きな組織で通用しなくなりそうだと感じている点

「デザインからフロントエンド、バックエンドまで全部を自分ひとりで通す」動き方は難しくなるだろうと考えている。
一方で、これまでメインはバックエンドであり、特に設計周りの技術力には自信がある。
そのため「**バックエンドを理解したフロントエンド**」としてなら価値が出せるのではないか、と捉えている。

事業責任者と直接話して合意を取る動き方が大きな組織で通用するかどうかについては、
現時点では解像度が低い部分もあるが、基本的には今の延長線上で対応できると考えている。
具体的には、関係者それぞれが「どんな情報を持っているか」「何の決定権を持っているか」を整理したうえで
話を進めればよいと捉えており、必ずしも自分が意思決定者に直接話を上げる必要はなく、
必要に応じて上長経由で上げてもらう形でも構わないというスタンス。

### 業務経験より前からある土台

- もともとデザインが好き。実績と呼べるものはほぼないが、趣味の範囲でグラフィックデザインやポスターデザインを行っている
- 個人開発でも、見た目にこだわったものを作るのが好き
  （現在開発中の[TRPGプレイヤー向け日程調整ツール](./projects/2026-trpg-schedule-adjustment-tool.md)がその実例）
- もともと目立ちたがり屋。学生時代はよく班長を務めていた。
  大学時代は50〜60人規模のサークルでサークル長を務め、イベントを主催したり活動を推進したりしていた。
  当時は「人がいっぱい集まっている」「人が楽しんでくれる」ことがいいと感じていた

#### 「自分が起点で作ったものに人が喜ぶ」という一貫した原体験（深掘りで判明）

現職での体験（UIリニューアル・リスクチェック機能）で初めてこの志向を持ったわけではなく、
本人の認識では**ずっと前から同じ考え方・気質があった**。次のエピソードが具体例。

- 昔から「幹事」的な役回りを好んで担ってきた。修学旅行の行き先などでも「絶対これが面白い」と
  思ったら自分から幹事に立候補し、自分が面白いと思ったものを形にしていた
- 大学のサークルでは、リーダーになる**前から**自分が面白いと思った企画・イベントを積極的に打ち、
  サークル全体を自分の好きな色に染めていった。やりたいと思ったことをやり、みんなが「面白い・楽しい」と
  言ってついてきてくれるのが楽しかった
- 現在のTRPG・アナログゲームのコミュニティ運営も同じ構造。自分が遊びたい人を集め、
  自分が楽しいと思ったイベントを開き、楽しいと言ってくれる人が集まって、笑顔で盛り上がってくれることに
  強い喜びを感じる

この喜びには**「自分がいいと思って作った／設計したものであること」が必須**だと本人は明言している。
他人が考えたものを実行してみんなが盛り上がっても、それはそれで楽しめるが、
**自分が考えたものが人に刺さっているときに一番プラスの感情が湧く**。ここが「単に人を喜ばせたい」
という一般的な貢献志向との違いにあたる。

そのうえで、「自分がいいと思ったものを人が使って・見て、楽しそう・幸せ・楽になっている」ことを
**最も強く感じられる形が、視覚的に見えて、場合によっては手で触れられるもの**だった。
それがアプリのUI・UX・体験や、ポスターなどのビジュアルデザインである。
だから今は、体験・UI・ビジュアルといった領域を追求する仕事をしていきたいと考えている。

### 「人のマネジメント志向」だと思っていた時期と、その捉え直し

新卒当時（入社面接時）は「ピープルマネジメントをしていきたい」「人の成長を後押しするようなことをやっていきたい」と話していた。
しかし最近になって、それは違ったかもしれないと考えるようになった。
実際には単純に目立ちたがり屋で、自分の思想を強く反映したイベントやサークルを動かすこと、そこに自分と同じ思想を持った人がいることが楽しかったのだろう、と捉え直している。
現在のTRPG・アナログゲームのコミュニティ運営も同じ構造だと本人は見ている。

### 業務での経験

[SEO対策ツール 記事作成機能 UIリニューアル](./projects/2025-seo-article-ui-renewal.md)と
[SEO対策ツール リスクチェック機能開発](./projects/2025-seo-risk-check-feature.md)は、
「すごく辛かったが、すごく楽しかった」と振り返っている。
ただし本人の認識では、これは原体験ではなく、それ以前にも同種の体験があったと感じている。

それ以前の業務で「楽しかった」と感じていたのは設計、特にアプリケーションレイヤーの設計。
もともとアプリケーションレイヤーの設計が好きで、自分としても一番自信がある箇所。
自分の考えが設計として採用されたときは楽しく、自分の思想が反映された「自分が思うきれいな設計」で開発ができているときには快感を覚えた。
UI/UXと同様、設計も「思想が色濃く出る」領域として本人の志向に含まれている。

### 技術投資の環境がないなかで、個人として動いた経験

「組織として技術投資できる環境がない」ことに対して、本人は個人での検証と社内への還元で対応してきた。
これは前述の「組織として技術・体験に投資できる環境」を求める理由の裏返しにあたる。

**業務外での検証**（いずれも個人の取り組み）

- Mago（PHP向けツール）の検証
- Mastra を用いたAIエージェント構築の検証（導入はしなかった）
- Laravel Cloud を個人で触り、感触を社内に共有
- Laravel AI SDK の検証

**業務内での取り組み**

- Claude Code の Skill / Subagent をプロダクトの開発フローへ組み込んだ。
  具体的にはリポジトリ内にSkillとSubagentを設定し、加えて自分が横で使って見せることで、
  その進め方を他のメンバーへ伝えた
- Figma Make を実験的に取り入れた
- Claude Code の導入自体はVPoEが行ったが、その「より良い使い方」の整備は本人が担当した。
  モデルの使い分けなどを含む

**社内ハンズオンの開催**

Claude Code の基本的な使い方と考え方を、ハンズオン形式で社内向けに開催し、
他のエンジニアが実際に使える形で還元した。扱った内容は以下。

- 初期設定から入り、単にメッセージを送るだけではない使い方
- セッションの概念、コンテキスト量の概念と、それに対して `/clear` が必要になる場面
- `/resume` で戻れること、rewind の使い方
- ガードレールを引くことである程度実装を任せられること
- 静的解析・テストと、それらを実行する基盤としての hooks・Skills
- CLAUDE.md に何を書くべきか。rules・Skills・Subagent にそれぞれ何を書くべきか

開催時期・回数は直近半年で2回。各回の参加人数は4名で、対象は自社開発室のエンジニア（全体で10名弱）。
参加者の経験年数は本人と同等か、それ以上のメンバー。

開催のきっかけは、Claude Codeの活用度に個人差があると感じたこと。
本人はもともとX（旧Twitter）や勉強会への参加、個人開発での試用を通じて知見があった一方、
そうでないメンバーは通常のChatGPTなどの使い方とあまり変わらない使い方に留まっていた。
AIの利用にはコストがかかる以上、開発生産性が向上していなければコストを投下する意味がなくなってしまうと考え、
自分の知識を組織に還元したいという思いから開催した。

成果としては、開発生産性の定量計測はできていない。
一方で定性的な変化として、単にAIにコードを書かせるだけでなく、Claude Codeに実装・テストを含めた品質チェックをさせ、
その結果を見て修正するというイテレーションを回せるようになった、という声を参加者から得ている。

改善の余地としては、開発生産性が上がったと言える指標を取れなかった点。
また、AIで開発を行うようになったことでボトルネックの位置が移動するはずで、
その先にどう対応すべきかを組織として踏み込んで考えたかった、という課題感を持っている。

### 本人が認識している直近の課題

自分が抱えているエネルギー源（欲求・思想）を、目の前にあるビジネス課題を解決するための燃料としてどう使うか。
発想の転換や、考えの紐付け（点と点を線にすること）が必要だと考えているが、そのやり方をまだつかみきれていないと自覚している。
### 取材管理システムの経験が「避けたいこと」の由来になっている

[新卒メディア向け取材管理システム](./projects/2026-media-interview-management-system.md)は、案件としては約6か月で切り出しているが、
実際には新卒の頃から担当しているシステムで、通算では6年目にあたる（間に1年ほど離れた時期はある）。本人が最も長く関わったシステム。

このシステムでも新規開発は行っていたが、費用対効果をかなり重視した結果、機能を削ったり、体験というよりも純粋な業務効率化（コミュニケーションコストの削減など）を進めることが多かった。
体験の部分にコストを割けないことが辛かった、と振り返っている。

一方で、いわゆるプロダクト開発にちゃんと参戦できたのは、SEO対策ツールに異動してUIリニューアル・リスクチェック機能を担当したときが初めてだった。
そこで経験した次のことが、非常に楽しかったと述べている。

- スピード感を持って、ちゃんとお金になる機能を作る
- 各社と連携してプロダクトをより良い方向にしていく
- その中で意見・提案を行い、それが反映される
- リリース後にユーザーが実際に使ってくれて、売上が上がった・改善したという結果につながる

そのため、こうしたことができるプロダクト・会社に関わりたい、かつ、より多くの人に影響を与えるシステムに携わりたいと考えている。
