# docs — 職務経歴の一次情報源

このディレクトリは、レジュメに書く内容の**事実の一次情報源**です。

ルールは1つです。

> **`docs/` にない実績は、レジュメに書かない。**

レジュメに書いたことは面接で必ず確認されます。ここにない話が載っていると、
本人が説明できず信頼を失うため、`docs/` の内容が事実の上限になります。
`/resume-build` はここにないことを書きませんし、`/resume-review` はここと突きあわせて検証します。

なお、リポジトリ直下の [`resume.md`](../resume.md) は過去に書いた古いドラフトであり、
一次情報源ではありません。内容の根拠には使いません。

## ファイル構成

| ファイル | 内容 |
| --- | --- |
| [`projects/`](./projects/) | 案件ごとの棚卸し。[`_template.md`](./projects/_template.md) をコピーして作る |
| [`skills.md`](./skills.md) | テクニカルスキルの棚卸し |
| [`activities.md`](./activities.md) | 登壇・執筆・OSSなどのアウトプット |
| [`career-vision.md`](./career-vision.md) | キャリアビジョン（レジュメの野望欄の元ネタ） |

## 書くときのルール

- **推測で埋めない。** 一般的にありそうな話で補完すると、それがレジュメに載って面接で破綻します
- 聞けていない・思い出せない項目には、HTMLコメントで `未ヒアリング` の印を残す
- 「大したことない」と思う経験も省かない。ニッチな技術経験、地味な運用改善、
  社内LT、個人開発なども企業の評価対象です。載せるかどうかはレジュメを作る段階で決めます
- 成果は数値で書く。数値がないものは「変化前 → 変化後」の対比で書く
- 技術は「プロジェクトで使われていた技術」と「自分が手を動かした技術」を必ず分ける

## レジュメ作成の流れ

```text
/resume-interview  → docs/ に一次情報源を書き溜める（壁打ち）
       ↓
/resume-build      → drafts/resume-v1.md を生成
       ↓
/resume-review     → 4観点のサブエージェントが drafts/reviews/v1-*.md を生成
       ↓
/resume-revise     → 採否を確認して drafts/resume-v2.md を生成
```

詳細は [リポジトリの説明](../README.md) を参照してください。
